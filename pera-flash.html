Pera Flash

A Japanese tutor you chat with. The model corrects your sentences and explains the grammar, and almost nothing else in the app ever calls it.

Open the app Read the code

The problem

A textbook can anticipate the mistakes it planned to teach. A tutor has to answer the sentence the learner actually wrote.

There is no finite list of those. Correcting free-form Japanese, saying which part is wrong and why, and doing it in whichever of six interface languages the learner reads, is genuinely the shape of problem a language model is good at. It is also close to the only part of this app that is. Everything the learner does with a correction afterwards, filing it, reviewing it, being quizzed on it, exporting it, is ordinary software, and building it that way is what keeps it free and offline.

How a reply gets made

Four objects and a controller. Exactly one of them names a model, so changing provider is a one-file change. Before that, the three model-backed features each called RubyLLM.chat directly and inherited whatever default the gem happened to ship, which meant a bundle update could change the model with no deploy and no diff.

  1. 01 MessagesController#create Saves what you wrote, hands back an empty bubble. The reply is a second request.
  2. 02 PeraReply Chooses what the model sees: recent turns, and the cards you keep failing.
  3. 03 PeraPrompt The instructions. Shares its furigana rule with the card generator, so a word taught in chat and the card made from it are annotated identically.
  4. 04 LlmChat The only place a model is named. Owns the credentials and the retry.
  5. 05 MessagesController#stream Server-sent events. Each one carries the whole reply so far, not a delta.

Reviewing a card, sitting a quiz, searching a deck and exporting to Anki never reach a model at all. All four are plain Ruby against Postgres. That is why they stay free, keep working when the provider is down, and cannot be taken out by somebody else's rate limit. The model corrects Japanese. Everything downstream of the correction is software that can be tested.

Thinking, turned off

Every token arrived at the very end, because the model was reasoning before it emitted anything.

The chat streams, so the number that matters is not how long a reply takes but how long the screen stays empty. With thinking on it stayed empty for the whole generation, because the budget is spent before the first token. Sixteen seconds of nothing, and once, thirty-eight.

Correcting a beginner's sentence into a known format is not what a thinking budget is for. Turning it off took first token from 16.3 s to 1.1 s, and the corrections came back just as good. The one trap is placement: thinkingBudget has to nest inside thinkingConfig, because at the top level of generationConfig the API rejects it as an unknown field rather than ignoring it.

A chat that got dearer the longer it ran

Message fifty carried the preceding forty-nine with it.

Every reply replayed the entire conversation, so the cost of a chat grew with the square of its length. A long lesson, which is the good outcome, was also the expensive one. Capping the replay at MAX_HISTORY_MESSAGES, which is 30, flattens the per-reply cost, and recent turns are what a tutor actually needs to stay coherent.

Before

Messages replayed per reply, against turn number. Nothing stops it, so the total for a conversation is the area under a diagonal.

After

The thirty most recent messages, replayed oldest first. Per-reply cost stops growing, and a long lesson costs what a short one does.

A cap alone would have made Pera forgetful, so the durable memory moved somewhere bounded and cheaper: the learner's own flashcards. STRUGGLING_LIMIT, which is 5, injects the cards they keep failing, drawn from every deck rather than this conversation, because what somebody keeps forgetting is a fact about them and not about where the card came from. Five is enough for Pera to find an opening and few enough that the instructions stay about teaching instead of becoming a list of failures.

There was a smaller bug hiding in the same method. The replayed history included the message being answered, which #ask sends anyway, so the model was shown every new message twice.

A quiz with no model in it

The wrong answers are the learner's own cards.

Multiple choice needs three plausible wrong answers, and generating them is the obvious job to hand a model. It is also the wrong one. Distractors sampled from the learner's other cards are better than generated ones, because they are the same person's material on the same topic, which makes them genuinely confusable rather than decoratively wrong.

They are also free, work offline, and cannot fail. QuizQuestion is not even an ActiveRecord model: a question has no life beyond the moment it is asked, and the card carries everything that outlasts it. The one subtlety is deduplication. Two cards that happen to share an answer would put the same text in two places, and the grader would mark one of them wrong.

Running on a handful of free keys

Quota on the free tier is per key, so one exhausted key would take the whole feature down until it reset. GEMINI_API_KEYS holds a comma-separated list, and LlmChat.with_chat catches a rate-limit error and yields a fresh chat on the next key. Only a rate-limit error: a malformed request is not going to succeed on different credentials, and retrying it would spend a second key's budget to produce the same failure.

That decision reaches further than it looks. The block has to perform the whole exchange rather than just build the chat, because a retry has to replay the instructions and the history against the new key. Which in turn is why the stream sends the whole reply so far on every event instead of a delta: if a key runs out mid-sentence, the reply starts over, and the browser redraws rather than showing the first half twice.

Two smaller things that were worth the time. The ensure that closes the stream wraps only the streaming, not the record lookup above it, because wrapping the lookup meant a 404 committed a 200 on its way out. And credentials_pinned_test guards against dotenv handing the test suite a real key: that already happened once, and the suite quietly spent live quota. Its assertions are bare assert with hand-written messages rather than assert_equal, because assert_equal would print the live key into the CI log on exactly the run that proves it is exposed.

A Rails 8 monolith on PostgreSQL, server-rendered with Hotwire and importmap, so there is no Node build step. It ships as a PWA in six languages. One file names the model; the rest of the app does not know there is one.
